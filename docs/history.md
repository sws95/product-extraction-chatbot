# 작업 경과 (claude.ai 대화에서 옮겨온 기록)

Claude Code가 이어서 작업할 수 있도록, 지금까지 무엇을 왜 결정했고 무엇이 남았는지 적어둔 문서입니다.
결정의 이유가 궁금하면 여기를 먼저 봅니다.

## 목표

GitHub 포트폴리오용 프로젝트. 추천과 광고 모델링, LLM 에이전트를 하는 ML 엔지니어가
"로컬 LLM으로 리뷰에서 구조화 정보를 뽑고, 근거를 코드로 검증하는 RAG 챗봇"을 보여주려는 것.
저장소 이름은 product-extraction-chatbot (예전 이름 llm_beauty).

## 주요 결정과 이유

| 결정 | 이유 |
|---|---|
| 데이터: Amazon Reviews 2023의 Amazon_Fashion | 이미 받아둠. Clothing_Shoes_and_Jewelry는 수십 GB라 보류. 상품이 부족하면 그때 전환 |
| 카테고리 대신 제목 단어로 아우터, 니트 선별 | Amazon_Fashion 메타의 categories가 100% 비어 있음 |
| 리뷰 10개 이상 조건 → 상품 1,462개가 전부 | 5,000개를 원했지만 이 카테고리엔 이만큼뿐 |
| LLM: Qwen3 4B 8비트 (Ollama) | 상품 10개 직접 채점에서 1.7B는 16비트여도 종류를 틀림(카디건을 pants). 4B 16비트는 8GB GPU에 안 들어감 |
| 임베딩, 리랭커는 CPU | 작은 모델이라 충분하고, GPU는 LLM에 전부 쓰기 위해 |
| Ollama 동시 처리 4개 | 4B 기준 요청당 KV 캐시 약 0.6GB. 8개는 8GB를 넘음 |
| 온도 0.3, top_p 0.8, top_k 20, seed 42 | Qwen3 모델 카드가 greedy 디코딩을 쓰지 말라고 함 (끝없는 반복). 답변도 0.7에서 0.3으로 되돌림: 0.7에선 형식을 덜 지킴 |
| Docker Desktop + WSL2 | 집 PC. 가상화 지원 오류는 VirtualMachinePlatform 기능 켜기로 해결 |

## 겪은 문제와 해결 (README의 "추출 품질을 높인 과정"과 같은 내용)

1. 모델이 선택지를 못 봄 → 프롬프트에 칸마다 선택지와 규칙 직접 기재
2. 기본값 있는 칸을 Ollama가 건너뜀 → 목록이 항상 비어 보임 → 모든 칸 필수
3. polyester 252번 반복 → 목록 최대 개수, 그리고 greedy 디코딩 중단
4. 원문에 없는 색, 소재 → configs의 grounding 단어로 사후 검증
5. 리뷰 측면의 지어낸 인용 → 인용 구절이 리뷰에 있는지 확인 (8% 제외)
6. 중복 리뷰 ID로 검색 에러 → 전처리, 인덱스, 검색 세 곳에서 중복 제거
7. 레깅스, 비니, 목욕 가운이 섞임 → 종류 other 제외 + 제목 단어 제외(index_exclude_title)
8. "그중에"를 새 추천으로 분류 → 코드 규칙으로 choose_from_shown
9. "털옷"을 종류로 안 좁힘, 프롬프트 예시가 새서 엉뚱한 측면 → 단어 목록(item_type_keywords, material_keywords, aspect_keywords)을 코드가 직접 적용
10. "언급 없음"인데 "털 덜 빠지는 제품으로 추천" → 물어본 측면의 결론은 코드가 작성(_focus_lead), 정렬은 평 좋음 > 정보 없음 > 평 나쁨
11. 같은 코트의 US 6, US 14가 따로 나옴 → 사이즈와 색을 뗀 제목으로 합치기(_base_title)
12. 답변이 영어 섞이고 길어 15초 → 한국어로 풀어 쓰기, 상품당 두 문장, 출력 상한
13. 근거 없는 문장 삭제가 너무 세서 답이 조각남 → 답변을 상품별 구조화 출력(AnswerOut)으로 받고 상품 단위로 검사, 다 지워지면 집계 문장으로 대체
14. 상품별 구조화 답변을 실제로 돌려보니 (2026-10-07): 모델이 상품 3개 중 1개만 채움, 코드가 쓴 결론을 도입과 맺음말에 되풀이, 맺음말에 '리뷰에서 확인되지 않아요' 채움 문장, 근거 없는 %를 도입에 씀
    → items 개수를 상품 수로 강제(min=max, Ollama가 llama.cpp 문법으로 minItems를 지킴), 검사할 수 없는 맺음말 칸 삭제, 결론이 있거나 숫자가 든 도입은 버림, %는 그 상품 집계 값과 대조, 채움 문장 쓰라는 규칙 삭제. check_all에 문장 반복과 채움 문장 검사 추가
15. 3턴 이상 돌려보니 "2번 사이즈는 어때?", "회색으로 다시 보여줘"를 모델이 '보여준 것 중 고르기'로 분류해 엉뚱하게 답함. "2번"도 1턴 순서로 찾아서 화면 번호와 어긋남
    → 사용자 결정으로 '보여준 것 중 고르기'(choose_from_shown)를 없앰. 매 턴 이전 턴 검색어와 이번 검색어를 합쳐 새로 검색 (8번의 결정을 대체, 예전에는 검색어를 턴 사이에 누적하지 않았음)
    → 모델이 query_en을 'recommend' 한 단어로 내서 측면을 놓치는 일이 있어, 메시지에서 코드가 찾은 측면을 검색어에 붙이고 빈말과 조건 값은 코드가 뺌
    → "n번"은 코드가 상품 질문으로, 번호는 매 검색 턴 화면 순서로 저장. 발라클라바(모자)가 옷으로 나와서 제목 제외 단어에 추가
16. "털 안 빠지는"이 단어 목록에 없어 털 빠짐으로 인식 안 됨 → 단어 목록을 늘리지 않고 모델이 측면과 근거 구절을 내게 함 (9번 문제 때문에 코드가 검사)
    → 모델은 구절을 그대로 옮기지 않고 "털 빠짐"처럼 줄여 써서, 완전 일치 대신 한글 글자 60% 이상 겹침으로 인정. 이전 턴 문장을 끌어온 구절("추위 많이 타는데")은 0%로 걸러짐
    → "회색으로"를 색감 측면으로 잡음. 프롬프트로 말해도 놓쳐서, 이번 턴에 색 조건이 바뀌면 모델이 고른 색감 측면은 버림
    → 한 상품 문단 안 같은 문장 반복(리뷰 번호만 다른 것 포함)은 코드가 한 번만 남김
17. 사용자 지적: 털 빠짐은 테스트 문장에 맞춘 과적합 → 측면 목록에서 shedding 삭제 (추출 결과는 그대로, 집계와 설정에서만 제외. 측면 문장은 검색 텍스트로 남음)
    → 목록에 없는 요구마다 기준선을 정해 "관련 리뷰 있음/없음"을 가르려다 사용자 지적으로 그만둠. 대신 요건별 가중치:
      이전 턴 요건과 이번 턴 요건을 리랭커가 따로 채점, 가중치 1:2로 합산 (특정 단어나 기준선 없음)
    → 모델은 측면 이름을 고르지 않고 원하는 점을 영어 구절 + 근거 구절로만 냄. 숫자 결론은 사용자가 직접 말한 측면(단어 목록)만.
      모델이 측면을 고르게 했더니 "털 안 빠지는"을 소재 품질로 골라 묻지 않은 결론이 붙었음. 색감 예외 규칙도 필요 없어져서 지움
    → 남은 한계: 이번 턴 요건의 질은 모델 번역에 달림 (같은 문장이 'no loose hair'로도 'fur free'로도 나옴)
18. 이어지는 턴에서 측면을 말하면 그 측면 만족 %로 순서를 통째로 다시 매기던 것(10번의 정렬)을 없앰 (사용자 결정, 중간안)
    → 리뷰 1건 100%가 20건 90%를 이기고, 이전 턴 요건이 순서에서 사라졌음. 가중치만 쓰면 리랭커가 주제만 보고 평의 좋고 나쁨은 못 가림
    → 측면 만족 %는 가산점으로만: 리뷰 5건분의 50%와 섞고(리뷰가 적으면 작아짐), 이번 턴 측면 2 이전 턴 1. tests/test_ranking.py로 확인
19. 답 문장이 인용 리뷰와 안 맞음 ("[R4] 털 안 빠지는 걸로 추천. 하지만 털이 많음"). 리뷰 번호만 확인해서 내용은 통과됐음.
    한 칸에 여러 문장을 넣으면 앞 문장의 %로 뒤 문장까지 통과하는 구멍도 있었음
    → 답변을 인용 먼저로: 근거마다 리뷰 번호 → 영어 원문 구절 → 그 구절만 근거로 한 문장. 구절이 그 리뷰 원문에 있을 때만 남김, 첫 문장만
      (Anthropic 'Reduce hallucinations'의 direct quotes, Constraint Tax 논문의 근거 칸 먼저. 리뷰 측면 추출의 인용 검사와 같은 방식)
    → 같은 4턴 대화 비교: 2턴이 기준은 3상품 모두 근거 없는 '털 안 빠지지 않다고 하네요', 인용 먼저는 실제 털 빠짐 리뷰를 인용
      (R7 'The fur on the inside gets every where'). 근거 18개 중 17개 원문 대조 통과, 다른 상품 리뷰를 댄 1개는 걸러짐
    → 답변 시간 턴마다 1.2~1.9초 늘어남 (8.9/6.6/2.7/8.7초 → 10.1/8.3/4.6/9.9초, 한 번씩 측정)
    → 남은 문제: 구절은 맞는데 한국어로 옮길 때 뜻이 틀림 ('pet hair MAGNET' → '털이 빠져나가기 쉬움', 'cool' → '시원한').
      한자 섞임, 영어 그대로는 코드가 버림. 뜻 검사는 NLI 검사기가 필요 (다음 할 일)
20. 사용자 지적: "털 안 빠지는 걸로"에 털 빠진다는 리뷰가 있는 상품을 추천함. 리랭커는 주제(털 빠짐 얘기)만 보고 방향(안 빠짐)은 못 가림
    → 근거마다 stance(원하는 점에 맞음/반대/무관)를 고르게 함 (리뷰 → 구절 → stance → 문장 순서). 원하는 점이 있으면 후보 5개를 읽혀
      반대 리뷰가 있는 상품을 뒤로 보내고 상위 3개만, 결론은 코드가 씀. 맞는 상품이 없으면 없다고 말하고 다음 질문을 한 번 제안 (사용자 제안)
    → 모델이 stance를 원하는 점과 상관없이 고름 (털 빠짐 기준인데 '따뜻해요'를 맞음, '안 따뜻해요'를 반대).
      인용마다 리랭커로 '이번 원하는 점'과 '이전 요건' 점수를 비교해서 이번 쪽이 높을 때만 stance 인정 (기준선 없음)
    → 메시지 전체를 옮긴 구절은 원하는 점으로 안 봄 (1턴이 후보 5개를 읽어 17초 걸리던 것 해결, 10.6초)
    → 확인: 'gray fuzz everywhere'(보풀이 사방에) 리뷰가 있는 상품은 상위 3개에서 빠짐. 'warm' 근거 4개는 무관으로 바뀜
    → 남은 문제: 맞음 판정 오류 ('Surprisingly soft sweater'를 털 안 빠짐 근거로 인정). 이번 턴 요구를 'fur free'로 잘못 번역한 영향도 큼

21. 반대 판정을 제대로 하기 (2026-10-08). 앞의 '맞음/반대' 측정은 원래 측면 추출 라벨로 했는데, 털 빠짐 라벨이 엉터리였음
    (배송 'Fast shipping'을 shedding 긍정으로, 'see through'를 shedding 부정으로). 그 수치들(19, 20번의 다국어 리랭커 비교 포함)은 믿을 수 없다.
    → 145개를 Claude가 직접 다시 라벨링 (data/eval/stance_set.json, 사람 검수 아님). 실제 반대 30개(털 빠짐 5, 사이즈 25)
    → 시도와 결과 (반대 찾음 / 반대라 한 것 중 진짜):
       답변 모델 판정 칸 0/30 (구절 하나씩 주면 전부 '무관'), 리랭커 상대 비교는 방향을 못 가림, 단어 규칙 0/30 (Qwen이 "털 안 빠지는"을 'Falls apart'로)
       번역 전용 모델(opus-mt, NLLB) 오역 심함, 지시문 리랭커 Qwen3-Reranker 10/30 정확하지만 CPU 10쌍 20초
       EXAONE 3.5 7.8B는 한국어 이해 최고(7개 요구 모두 맞게 옮김)지만 GPU 7GB를 써서 Qwen과 같이 못 씀
       NLI large + 고정 가설 3/5, 4/25, NLI 가설을 원하는 점(긍정문)으로 두면 아무 불만이나 모순으로 봐서 오판 많음
    → 찾은 핵심: Qwen은 한국어 개념은 대체로 알아듣는데 '안'을 뒤집는 방향을 틀림. 한국어 부정을 코드가 떼어 내면
      (털 안 빠지는 → 털 빠지는) 번역만 하면 돼서 문제 문장이 맞게 나옴 (9개 요구 중 7개)
    → 채택: 부정 떼어 내기 + Qwen 번역 → DeBERTa-v3-large NLI 함의면 반대 확정 (실제 경로로 10/30, 반대라 한 것 모두 진짜).
      LLM 예/아니오 확률(Ollama logprobs)로만 반대면 순위만 내림 (둘을 합치면 16/30, 84%). src/agent/stance.py, scripts/eval_stance.py
    → NLI가 느렸던 이유: 모델이 fp16으로 저장돼 있어 CPU에서 fp16으로 돌았음. float32로 올리니 10쌍 4.8초 → 1.3초. int8 양자화는 판정이 망가짐
    → 이번 턴 검색 요건도 모델의 영어('fur free', 'fur' 등 실행마다 다름) 대신 이 문제 문장을 씀
    → 답변 모델의 stance 칸, 다국어 리랭커 검사는 지움. 실험에 받은 모델 약 17GB 삭제
